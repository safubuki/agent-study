**一番大事な結論を 3 行で**：

1. スキルは「呼ばれたら良い仕事をする手順書」として磨く。「必ず呼ばれること」「必ず守られること」はスキル以外（フック・権限・常時の指示・専用エージェント）に任せる。
2. 階層はスキルの説明文ではなく**置き場所と仕組みの強さ**で表す。説明文は「同じ層の中で、どの手順を使うか」を選ぶためだけに使う。
3. 改善ループは自動化してよいが、**採用は人**。増やすだけでなく、棚卸しで減らす。

共通の棚卸しスクリプト（[shared/skill-catalog](shared/README.md)）を、`C:\git_home\turtle-skills-neo\full-skills\.github\skills` に**読み取りだけで**実行しました（2026-11-18）。


| 項目 | 結果 |
|---|---|
| スキル数 | 36（手動専用 0、`paths` で範囲限定 0 → **36 個すべてが説明文による自動発火の対象**） |
| 説明文の合計 | 8,471 文字（1 件あたり平均約 235 文字、最長 577 文字。すべて標準の上限 1,024 文字以内） |
| 本文 500 行超 | なし（最長 360 行） |
| 説明文の重なり | 2 組 |
| リンク切れ（error） | 8 件（3 スキル） |
| 「いつ使うか」の手がかりが見当たらない（info） | 3 件 |

**見つかったことと、その読み方**：

1. **同じ発火キーワードの重なり（2 組）**
   - `remo-composition` ⇔ `remo-sound-designer`：「BGMを入れて」「音量調整」「bgm」が両方の説明文にある。「BGM を入れて」と頼むと、どちらが呼ばれるかは AI の判断次第になります。どちらが担当かを決め、もう一方の説明文から外すか、「〜は remo-sound-designer を使う」と書き分けるのがおすすめです。
   - `turtle-ai-quartet-hub-overview` ⇔ `turtle-video-overview`：「アーキテクチャ」が重なっている。別プロジェクトの概要スキルどうしなので、**それぞれのプロジェクトのリポジトリにだけ置く**（集約リポジトリからは配らない）と競合しません（Claude Code なら `paths` で限定する方法もある）。
2. **リンク切れ 8 件はすべて「プロジェクト直下のファイルへのリンク」**（例：`../../../spec.md`、`../../../package.json`）。元のプロジェクトでは正しく、**スキル集に集約した時点で切れる**種類のものです。これは「プロジェクト専用スキル」と「どこでも使える汎用スキル」が同じ場所に混ざっている印なので、集約リポジトリでは区分（`metadata` 欄やフォルダ分け）を付けると、配る範囲を判断しやすくなります。
3. **36 個すべてが自動発火**。`release-version-manager`・`skills-sync-guard`・`skill-update` のように**ファイルを書き換える・同期する**スキルは、`disable-model-invocation: true`（人が `/名前` で呼んだときだけ）にすると、誤発火の心配と一覧の負担が減ります。この欄は Claude Code だけでなく **VS Code の Copilot でも使えます**（1 回目の報告では「Copilot では無視される」と書きましたが、VS Code の公式資料で対応を確認したので訂正します）。
4. 利用ログを付けていないので「使われていないスキル」はまだ分かりません。[shared/hooks](shared/hooks/log-skill-usage.js) のフック（設定は [Copilot 版](copilot/samples/02-skill-usage-log/README.md)・[Claude Code 版](claude/samples/02-skill-usage-log/README.md)）で 2〜4 週間記録してから、`--usage` 付きで再実行すると、棚卸しの候補が出ます。

> [!NOTE]
> 上の提案は判断材料です。どのスキルを手動専用にするか、どれを集約リポジトリから外すかは、実際の使い方に合わせて決めてください。スクリプトは読み取りだけで、元のフォルダには何も書き込んでいません。
